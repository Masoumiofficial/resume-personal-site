# گزارش فاز ۶: استقرار

> **وضعیت:** بخش مستقل از هاست انجام و تست شده است. **اجرا روی هاست انجام نشده**، چون به هاست دسترسی نداریم. مراحل اجرا در [راهنمای استقرار](deployment-guide.md) آمده و نتیجهٔ واقعی آن را تست خودکار بخش ۱۰ راهنما نشان می‌دهد.

## هدف

سایت باید روی هاست اشتراکی DirectAdmin، بدون Node، Composer، SSH یا worker، امن و قابل بازگشت مستقر شود. پشتیبان‌گیری و تست بازگردانی و جایگزینی وردپرس بدون از دست رفتن نشانی‌ها هم جزو هدف است.

## کارهای انجام‌شده

1. **پشتیبان‌گیری و بازگردانی (D35):**
   - فرمان‌های `app:backup` و `app:restore` به PHP خالص نوشته شده‌اند.
   - قالب پشتیبان مستقل از موتور دیتابیس است.
   - پیش از بازگردانی، یک پشتیبان ایمنی گرفته می‌شود.
   - پشتیبانِ گرفته‌شده با کد جدیدتر رد می‌شود.
   - نگهداری نسخه‌ها و زمان‌بندی روزانه و هفتگی دارد.
2. **فرمان `app:deploy` (D40):**
   - یک فرمان idempotent برای نصب و به‌روزرسانی است و با یک Cron یک‌باره روی هاست بدون SSH اجرا می‌شود.
   - گزینهٔ `app:create-admin --generate-password` رمز را در فایل خصوصی می‌نویسد.
3. **Document Root تغییرناپذیر (D36):** چیدمان جدا با `app-path.php` و `bootstrap/public-path.php` پشتیبانی می‌شود، از جمله برای زیردامنه‌ای که وب‌روتش داخل `public_html` است.
4. **آپلودهای قدیمی (D37):** `public/wp-content/uploads/.htaccess` فقط تصویر و PDF را سرو می‌کند.
5. **تست پس از استقرار (D38):**
   - اسکریپت `tools/smoke/smoke.php` حدود ۴۰ بررسی انجام می‌دهد، به‌علاوهٔ هر ۵۹ قانون انتقال.
   - workflow دستی `smoke.yml` آن را روی سرور GitHub اجرا می‌کند.
6. **بستهٔ انتشار (D39):** `release.yml` بسته را می‌سازد، در حالت production بالا می‌آورد و در هر دو چیدمان تست می‌کند. روی تگ `v*` هم GitHub Release منتشر می‌کند.
7. **ایندکس روی نصب تازه خاموش (D41)** و **`noindex` پنل در production**. خطای دوم را تست بسته پیدا کرد.
8. **بررسی production:** موارد سن آخرین پشتیبان، فایل رمز مدیر، و چیدمان وب‌روت اضافه شد. یک fallback برای `mod_deflate` هم اضافه شد.
9. [راهنمای استقرار](deployment-guide.md) به فارسی نوشته شد. چک‌لیست باقی‌ماندهٔ فاز ۵، یعنی آپلودها و TTFB و پشتیبان، در آن ادغام شده است.

## تست‌ها و نتایج واقعی

- **PHPUnit در محیط توسعه:** ۱۷۸ تست و ۱۱۳۶ assertion روی PHP 8.3 و 8.4، همه موفق. Pint روی ۱۵۳ فایل بدون خطا.
- **CI:** هر ۸ بررسی روی GitHub سبز است:
  - تست‌ها روی SQLite، MySQL 8.0 و MariaDB 10.3. تست رفت‌وبرگشت پشتیبان روی هر سه موتور اجرا می‌شود.
  - بستهٔ انتشار. آخرین اجرای بستهٔ نهایی در بخش «وضعیت انتشار» پایین آمده است.
- **بستهٔ انتشار روی سرور GitHub:**
  - اندازهٔ artifact حدود ۷٫۹ مگابایت است.
  - `app:deploy` در حالت production کلید ساخت، migrate، درون‌ریزی و ساخت مدیر را انجام داد. اجرای دوم آن «already deployed» گزارش داد.
  - `app:backup --media` و `app:restore` و `optimize` موفق اجرا شدند.
  - تست HTTP بدون هیچ FAIL گذشت. ۴ هشدار ماند که مخصوص `php -S` است: نبود HTTPS، فشرده‌سازی، کش فایل‌های ثابت و آپلودهای قدیمی.
  - چیدمان جدا در یک وب‌روت جدا هم تست HTTP را گذراند.
- **چیدمان جدا در محیط توسعه:** پوشه‌های `site-app` و `public_html` با php-wasm شبیه‌سازی شدند.
  - صفحهٔ اول ۲۰۰ برگرداند و CSS با `?v=mtime` از وب‌روت جدا بارگذاری شد.
  - `public_path` در خط فرمان، با کش تنظیمات، درست بود.
  - پشتیبان و بازگردانی روی دادهٔ پیش‌نمایش (۱۴۷ ردیف) انجام شد و صفحهٔ اول پس از بازگردانی بایت‌به‌بایت یکسان بود.
- **تست HTTP روی پیش‌نمایش محلی:** هر ۵۹ قانون انتقال درست بودند. `/media/.htaccess` با ۲۰۰ سرو شد، چون سرور php-wasm فایل‌های `.htaccess` را اعمال نمی‌کند. این بررسی برای هاست واقعی نوشته شده است.

## مشکلات و ریسک‌ها

1. **روی هاست اجرا نشده است.** این موارد فقط با اجرای راهنما معلوم می‌شود:
   - مسیر PHP خط فرمان
   - امکان تغییر Document Root یا دنبال شدن symlink
   - نسخهٔ دیتابیس
   - فشرده‌سازی و TTFB
2. **PHP 8.1 هاست** باید ارتقا یابد. اگر نسخه برای کل حساب عوض شود، روی وردپرس فعلی هم اثر می‌گذارد.
3. **`.htaccess` وردپرس در پوشهٔ والد:** وب‌روت پیش‌فرض زیردامنه داخل `public_html` وردپرس است. قواعد rewrite ارث‌بری نمی‌شوند، ولی سایر دستورها ممکن است اعمال شوند. تست بخش ۱۰ روی سایت آزمایشی این را نشان می‌دهد.
4. **پشتیبان روی همان هاست است.** بدون دانلود منظم یا پشتیبان بیرونی، در برابر از دست رفتن هاست محافظت نمی‌شوید.
5. **پیش‌نمایش محلی:** در این فاز اشکالی رخ نداد. تست‌ها با `DatabaseMigrations` روی دیتابیس `:memory:` اجرا شدند.
6. **دکمهٔ اجرای دستی تست:** این دکمه فقط پس از merge به `main` دیده می‌شود. اجرای پایه روی سایت وردپرسی فعلی به همین دلیل انجام نشد.

## معیارهای پذیرش

| معیار | وضعیت |
|---|---|
| بدون Node، Redis، Docker یا worker در production | ✅ |
| Document Root روی `public/` و بدون قرار دادن کل پروژه در `public_html` | ✅ سه روش. چیدمان جدا در CI تست شد. |
| ساخت محلی در صورت نبود SSH یا Composer | ✅ بستهٔ قابل بازتولید با `vendor` و بدون ابزار توسعه |
| پشتیبان‌گیری و **تست بازگردانی** | ✅ در کد و CI. ⏳ تست روی هاست در بخش ۱۱ راهنماست. |
| تگ انتشار | ⏳ بخش «وضعیت انتشار» پایین |
| استقرار روی هاست، سوئیچ نهایی و انتقال `.ir` | ⏳ منتظر اقدام مالک سایت |

## نیاز به اقدام مالک سایت

1. پاسخ به پرسش‌های پایانی، که در خلاصهٔ فاز آمده‌اند.
2. ارتقای PHP و ساخت زیردامنهٔ `staging` و دیتابیس، سپس اجرای راهنما از بخش ۱ تا ۱۱.
3. merge این شاخه به `main`، تا دکمهٔ تست خودکار ظاهر شود.
