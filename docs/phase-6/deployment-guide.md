# راهنمای استقرار روی هاست اشتراکی (DirectAdmin)

این راهنما برای جایگزینی سایت وردپرسی فعلی `sajadmasoumi.com` با سایت جدید است. هیچ مرحله‌ای سایت فعلی را حذف نمی‌کند. وردپرس تا پایان کار سر جایش می‌ماند و بازگشت به آن چند دقیقه طول می‌کشد.

## آنچه تأیید شده و آنچه نشده

**تأییدشده (CI روی GitHub Actions، هر push):**

- بستهٔ نهایی بدون ابزارهای توسعه ساخته می‌شود.
- بسته با `APP_ENV=production` روی PHP 8.3 بالا می‌آید.
- `app:deploy` اول نصب می‌کند و اجرای دوم کاری انجام نمی‌دهد.
- پشتیبان‌گیری و بازگردانی کار می‌کند.
- تست HTTP روی بسته اجرا می‌شود، با هر دو چیدمان پوشه‌ها (بخش ۴).
- تست‌های کامل روی MySQL 8.0 و MariaDB 10.3 اجرا می‌شوند.

**تأییدنشده (به هاست دسترسی نداریم):**

- مسیر دقیق منوهای DirectAdmin شما
- مسیر PHP خط فرمان
- امکان تغییر Document Root
- نسخهٔ دیتابیس
- فشرده‌سازی و سرعت پاسخ سرور

هرجا عبارت «**بررسی کنید**» آمده، مقدار به هاست بستگی دارد. بعد از هر مرحلهٔ مهم، تست خودکار بخش ۱۰ نتیجهٔ واقعی را نشان می‌دهد.

> **هیچ رمز، توکن یا محتوای `.env` را در چت، ایمیل یا مخزن Git قرار ندهید.**

## ۱. انتخاب نسخهٔ PHP

1. در DirectAdmin برای **زیردامنهٔ آزمایشی** (بخش ۴)، نسخهٔ PHP را 8.4 بگذارید. اگر 8.4 نبود، 8.3.
   - **بررسی کنید:** آیا تغییر نسخه فقط برای همان زیردامنه ممکن است؟ اگر نسخه برای کل حساب عوض شود، وردپرس فعلی هم با PHP جدید اجرا می‌شود. معمولاً وردپرس به‌روز با 8.3 و 8.4 مشکلی ندارد، ولی بهتر است قبلش از وردپرس پشتیبان بگیرید.
2. افزونه‌های جدول بالا را فعال کنید.

## ۲. ساخت دیتابیس

1. MySQL Management › Create new database.
2. یک نام و کاربر بسازید و یک رمز قوی تولید کنید.
3. رمز را فقط در Password Manager نگه دارید.
4. برای سایت آزمایشی و سایت اصلی **دو دیتابیس جدا** بسازید.

دیتابیس وردپرس دست نمی‌خورد.

## ۳. دریافت بسته و بررسی SHA-256

- **نسخهٔ منتشرشده:** صفحهٔ Releases مخزن. فایل `sajadmasoumi-site-vX.Y.Z.zip` و فایل `.sha256` را دانلود کنید.
- **آخرین ساخت یک شاخه:** Actions › Release package › آخرین اجرای سبز › Artifacts › `release-package`.

بررسی سالم بودن فایل در ویندوز:

```text
certutil -hashfile sajadmasoumi-site-v1.0.0-rc.1.zip SHA256
```

خروجی باید با محتوای فایل `.sha256` یکی باشد.

بسته شامل پوشهٔ `site/` است، با `vendor/` آماده. داخل آن `tests`، `docs`، `tools`، `.env` و ابزارهای توسعه **نیست**. CI این را بررسی می‌کند.

## ۴. چیدمان پوشه‌ها: کدام روش؟

قانون اصلی: **فقط محتوای `public/` باید از وب قابل دسترسی باشد.** پروژهٔ کامل هرگز نباید داخل `public_html` قرار بگیرد، چون `.env` و `storage` و `vendor` آنجا در معرض دید قرار می‌گیرند.

در DirectAdmin معمولاً این مسیرها را دارید. **بررسی کنید.**

```text
/home/USER/domains/sajadmasoumi.com/public_html/           ← وب‌روت دامنهٔ اصلی (وردپرس فعلی)
/home/USER/domains/sajadmasoumi.com/public_html/staging/   ← وب‌روت پیش‌فرض زیردامنهٔ staging
```

| روش | چه می‌کند | کی |
|---|---|---|
| **A. تغییر Document Root** | وب‌روت دامنه به `.../site/public` اشاره می‌کند. | اگر پنل یا پشتیبانی هاست این امکان را بدهد. **تمیزترین روش.** بازگشت = برگرداندن مسیر. |
| **B. پیوند نمادین (symlink)** | `public_html` به `site/public` لینک می‌شود. | بدون SSH هم با یک Cron یک‌باره ممکن است (بخش ۷). بازگشت = برداشتن لینک. |
| **C. چیدمان جدا** | محتوای `public/` در وب‌روت و پروژه در پوشه‌ای بیرون از آن. | اگر A و B ممکن نبود. |

### روش A

`site/` را در `/home/USER/domains/sajadmasoumi.com/site` استخراج کنید (بخش ۵). سپس Document Root را به `.../site/public` تغییر دهید.

### روش B

پوشه را مثل روش A استخراج کنید. بعد دستور این روش را اجرا کنید: با SSH، یا با Cron یک‌باره (بخش ۷).

برای زیردامنهٔ آزمایشی:

```sh
mv ~/domains/sajadmasoumi.com/public_html/staging ~/domains/sajadmasoumi.com/public_html/staging.old && ln -s ~/domains/sajadmasoumi.com/site-staging/public ~/domains/sajadmasoumi.com/public_html/staging
```

برای دامنهٔ اصلی، این دستور در زمان سوئیچ نهایی (بخش ۱۴) اجرا می‌شود:

```sh
mv ~/domains/sajadmasoumi.com/public_html ~/domains/sajadmasoumi.com/wordpress-old && ln -s ~/domains/sajadmasoumi.com/site/public ~/domains/sajadmasoumi.com/public_html
```

**بررسی کنید:** وب‌سرور باید پیوند نمادین را دنبال کند (FollowSymLinks / SymLinksIfOwnerMatch). تست بخش ۱۰ این را نشان می‌دهد.

### روش C

1. محتوای پوشهٔ `site/public/` را در وب‌روت بگذارید. این شامل فایل‌های مخفی هم می‌شود: `.htaccess` و `media/.htaccess` و `wp-content/uploads/.htaccess`.
2. بقیهٔ `site/` را در پوشه‌ای **بیرون از هر وب‌روت** بگذارید. مثلاً `~/domains/sajadmasoumi.com/site-app` و پوشهٔ `public` داخل آن را حذف کنید.
3. در **وب‌روت**، فایل `app-path.php` بسازید (نمونه: `bootstrap/app-path.example.php`):

   ```php
   <?php return '/home/USER/domains/sajadmasoumi.com/site-app';
   ```

   اگر پوشهٔ پروژه دقیقاً کنار وب‌روت باشد و نامش `site-app` باشد، این فایل لازم نیست.
   - برای زیردامنه که وب‌روتش **داخل** `public_html` است، این فایل **لازم است**. در غیر این صورت `../site-app` به داخل `public_html` اشاره می‌کند.
4. در **پروژه**، فایل `bootstrap/public-path.php` بسازید (نمونه: `bootstrap/public-path.example.php`):

   ```php
   <?php return '/home/USER/domains/sajadmasoumi.com/public_html/staging';
   ```

   این فایل لازم است تا آپلودها و فرمان‌های Cron مسیر درست `media/` را بدانند.
5. `php artisan app:check-production` باید این دو مورد را «OK» نشان دهد: «Web root has index.php and .htaccess» و «Project is not inside the web root».

## ۵. آپلود و استخراج

1. File Manager › پوشهٔ `domains/sajadmasoumi.com/`.
2. فایل zip را آپلود کنید. حدود ۸ مگابایت است. سقف آپلود هاست ۶۴ مگابایت است.
3. Extract کنید. پوشهٔ `site/` ساخته می‌شود. برای سایت آزمایشی آن را به `site-staging` تغییر نام دهید.
4. مجوزها: پوشه‌های `storage/` و `bootstrap/cache/` و `public/media/` باید برای کاربر شما قابل نوشتن باشند. پیش‌فرض DirectAdmin معمولاً کافی است. مجوز **777 ندهید**.

## ۶. فایل `.env`

1. در پوشهٔ پروژه، `.env.production.example` را به `.env` کپی کنید و ویرایش کنید.
2. این مقادیر را تنظیم کنید:
   - `APP_URL=https://staging.sajadmasoumi.com`: برای سایت آزمایشی. برای سایت اصلی `https://sajadmasoumi.com`.
   - `DB_DATABASE`، `DB_USERNAME`، `DB_PASSWORD`: از بخش ۲.
   - `ADMIN_PATH`: یک مسیر غیرقابل حدس برای پنل، فقط حروف کوچک، رقم و خط تیره. مثلاً `panel-7k2m`.
   - `APP_KEY` را **خالی بگذارید**. `app:deploy` آن را یک‌بار می‌سازد و هرگز عوض نمی‌کند.
3. **سایت آزمایشی هم `APP_ENV=production` بماند.**
   - تست‌ها و هدرهای امنیتی همان رفتار سایت اصلی را نشان می‌دهند.
   - ایندکس شدن آن با تنظیم «ایندکس موتورهای جست‌وجو» بسته است. روی دیتابیس تازه این تنظیم خاموش است (D41).
4. یک نسخه از `.env` سایت اصلی را در جای امنی **جدا از پشتیبان‌ها** نگه دارید. رمزهای 2FA با `APP_KEY` رمز شده‌اند.

## ۷. اجرای نصب

### با SSH

```sh
cd ~/domains/sajadmasoumi.com/site-staging
php artisan app:deploy --admin-name="سجاد معصومی" --admin-email="info@sajadmasoumi.com"
```

### بدون SSH: Cron یک‌باره

1. ابتدا مسیر PHP خط فرمان را پیدا کنید. یک Cron با زمان‌بندی «هر دقیقه» (`* * * * *`) بسازید:

   ```sh
   /usr/local/bin/php -v > ~/php-cli-version.txt 2>&1
   ```

   یک دقیقه بعد فایل را در File Manager باز کنید.
   - باید 8.3 یا 8.4 ببینید.
   - اگر نسخه قدیمی بود، مسیرهای رایج دیگر را امتحان کنید: `/usr/local/php84/bin/php`، `/opt/alt/php84/usr/bin/php` (CloudLinux)، یا مشابه آن‌ها برای 8.3.
   - **Cron را حذف کنید.**
2. Cron نصب، هر دقیقه (`PHP` = مسیر مرحلهٔ ۱):

   ```sh
   cd ~/domains/sajadmasoumi.com/site-staging && PHP artisan app:deploy --admin-name="Sajad" --admin-email="info@sajadmasoumi.com" > storage/logs/deploy-output.txt 2>&1
   ```

3. یک تا دو دقیقه بعد، `storage/logs/deploy-output.txt` را بخوانید. باید «Deploy finished» و جدول بررسی production را ببینید. **سپس Cron را حذف کنید.**
   - اگر حذف Cron یادتان رفت، اشکالی ندارد. اجرای دوباره همان نسخه فقط می‌نویسد «already deployed».
4. رمز پنل در `storage/app/private/initial-admin-password.txt` نوشته شده است. هرگز در خروجی Cron چاپ نمی‌شود.
   - آن را بخوانید و **فایل را حذف کنید.**
   - تا فایل حذف نشود، `app:check-production` «FAIL» نشان می‌دهد.

`app:deploy` این کارها را انجام می‌دهد:

1. پاک کردن کش‌ها
2. ساخت `APP_KEY` اگر خالی باشد
3. اجرای migrationها
4. درون‌ریزی محتوای بازبینی‌شده و خاموش کردن ایندکس، **فقط روی دیتابیس خالی**
5. ساخت حساب مدیر، فقط اگر هیچ حسابی نباشد
6. ساخت کش‌ها
7. اجرای `app:check-production`

## ۸. Cron دائمی (زمان‌بند)

یک خط با اجرای هر دقیقه:

```sh
cd ~/domains/sajadmasoumi.com/site && PHP artisan schedule:run > /dev/null 2>&1
```

| زمان | کار |
|---|---|
| هر روز ۰۳:۰۰ | پشتیبان دیتابیس |
| یکشنبه‌ها ۰۳:۱۰ | پشتیبان دیتابیس و رسانه |
| هر روز ۰۳:۳۰ | حذف پیام‌های تماس قدیمی، طبق تنظیم نگهداری |

اگر هاست Cron هر دقیقه را اجازه ندهد، هر ۵ دقیقه هم کار می‌کند. ساعت‌ها به وقت UTC سرور است.

## ۹. اولین ورود به پنل

1. نشانی `https://staging.sajadmasoumi.com/ADMIN_PATH/login` را باز کنید.
2. **رمز را عوض کنید** و **ورود دومرحله‌ای (2FA) را فعال کنید.** کدهای بازیابی را در Password Manager نگه دارید.
3. پروفایل:
   - عکس پروفایل را آپلود کنید.
   - عنوان حرفه‌ای و لینک شبکه‌های اجتماعی را بازبینی کنید.
4. دو مقالهٔ بازنویسی‌شده پیش‌نویس‌اند (D30). اگر مایلید منتشر کنید.
5. خدمت «مجوز ساماندهی» پیش‌نویس است. قیمت آن باید روشن شود.

## ۱۰. تست خودکار سایت (از GitHub)

1. در مخزن: **Actions › Smoke test (deployed site) › Run workflow**.
2. نشانی را بدهید (مثلاً `https://staging.sajadmasoumi.com`) و `admin_path` را وارد کنید.
3. GitHub به هاست دسترسی دارد. نتیجه به‌صورت جدول در Summary همان اجرا نمایش داده می‌شود.

موارد بررسی‌شده:

- انتقال http به https
- هدرهای امنیتی (CSP، HSTS، X-Frame-Options، nosniff، Referrer-Policy)
- صفحه‌های اصلی، robots، sitemap، feed و `/up`
- اسلش انتهایی، 404 واقعی (بدون انتقال به صفحهٔ اول) و `noindex` پنل
- **سرو نشدن** این فایل‌ها: `.env`، `composer.json`، `vendor`، لاگ‌ها، `.git`، فایل لاگ عمومی قدیمی وردپرس
- همهٔ **۵۹ قانون انتقال** نشانی‌های قدیمی (۳۰۱/۴۱۰)
- فشرده‌سازی، کش طولانی فایل‌های ثابت، و TTFB: میانهٔ ۵ درخواست از سرور GitHub. **این عدد تجربهٔ کاربر واقعی نیست.**

دکمهٔ Run workflow فقط وقتی دیده می‌شود که این workflow در شاخهٔ اصلی (`main`) باشد.

اجرای دستی از هر سیستم دارای PHP:

```sh
php tools/smoke/smoke.php https://staging.sajadmasoumi.com --admin-path=panel-7k2m
```

## ۱۱. پشتیبان‌گیری و **تست بازگردانی**

### فرمان‌ها

- `php artisan app:backup` (با `--media` برای رسانه هم)
- فایل‌ها در `storage/app/backups/` ذخیره می‌شوند، با مجوز 0600:
  - `db-*.jsonl.gz`: دیتابیس. مستقل از نوع موتور است و روی MySQL، MariaDB و SQLite برمی‌گردد.
  - `media-*.tar`: رسانه.
- `php artisan app:restore db-YYYYmmdd-HHMMSS.jsonl.gz [--media=media-....tar] --force`
  - **همهٔ داده‌های فعلی را جایگزین می‌کند.**
  - قبل از شروع، خودش یک پشتیبان «pre-restore» می‌گیرد. اگر بازگردانی خطا بدهد، فرمان برگشت به همان پشتیبان را چاپ می‌کند.
  - پشتیبانی را که با نسخهٔ جدیدتر کد گرفته شده رد می‌کند.

### نکته‌های مهم

- **پشتیبان روی همان هاست، پشتیبان نیست.** هفته‌ای یک‌بار جدیدترین فایل‌ها را از File Manager دانلود کنید. یا از پشتیبان‌گیری DirectAdmin به مقصد بیرونی استفاده کنید. **بررسی کنید** چنین امکانی دارید یا نه.
- پیام‌های تماس، داده‌های شخصی‌اند. فایل پشتیبان را رمزدار یا در جای امن نگه دارید.

### تست بازگردانی (یک‌بار پیش از سوئیچ، سپس هر چند ماه)

1. یک پشتیبان از سایت اصلی دانلود کنید.
2. آن را در `storage/app/backups/` سایت آزمایشی آپلود کنید.
3. با Cron یک‌باره اجرا کنید:

   ```sh
   cd ~/domains/sajadmasoumi.com/site-staging && PHP artisan app:restore FILE --force > storage/logs/restore-output.txt 2>&1
   ```

4. خروجی را بخوانید و Cron را حذف کنید. سایت آزمایشی را با تست بخش ۱۰ و چند صفحه در مرورگر بررسی کنید.

## ۱۲. کپی آپلودهای قدیمی وردپرس

مقاله‌ها و سایت‌های دیگر به نشانی‌های `/wp-content/uploads/...` لینک داده‌اند.

1. با File Manager پوشه‌های سال/ماه را کپی کنید: از `public_html/wp-content/uploads/` به `site/public/wp-content/uploads/`.
2. پوشه‌های افزونه‌ها (مثل `elementor`، `wc-logs` یا `cache`) و فایل‌های غیرتصویری را **کپی نکنید.**
3. فایل `.htaccess` همان پوشه فقط تصویر و PDF را سرو می‌کند و اجرای هر اسکریپتی را می‌بندد (D37). فایل لاگ عمومی `2024/10/log_file_2024-10-16__09-06-50.txt` حتی اگر کپی شود، سرو نمی‌شود. بهتر است اصلاً کپی نشود.
4. پیشنهاد: تصویرهای مقاله‌ها را بعداً از پنل در «رسانه» آپلود کنید و نشانی را در متن مقاله عوض کنید.

## ۱۳. اندازه‌گیری سرعت روی هاست

- تست بخش ۱۰ میانهٔ TTFB را گزارش می‌دهد.
- اگر به‌طور پایدار بیشتر از **۶۰۰ میلی‌ثانیه** بود (D33)، این موارد را بررسی کنید:
  - روشن بودن OPcache
  - اجرا شدن `optimize`. `app:deploy` این کار را انجام می‌دهد.
  - منابع پلن هاست
- نتایج آزمایشگاهی فاز ۵ مربوط به محیط محلی است، نه هاست.

## ۱۴. سوئیچ نهایی

یک ساعت کم‌بازدید را انتخاب کنید.

1. **پشتیبان کامل وردپرس:** پشتیبان DirectAdmin و خروجی دیتابیس در phpMyAdmin. هر دو را دانلود کنید.
2. نسخهٔ PHP دامنهٔ اصلی را 8.4 کنید (بخش ۱).
3. بسته را در `domains/sajadmasoumi.com/site` استخراج کنید.
   - `.env` با `APP_URL=https://sajadmasoumi.com` و دیتابیس سایت اصلی.
   - `app:deploy` را با Cron یک‌باره اجرا کنید.
   - یا: پشتیبان سایت آزمایشی را با `app:restore` روی آن برگردانید، تا محتوای ویرایش‌شده منتقل شود.
4. آپلودهای قدیمی را کپی کنید (بخش ۱۲). این کار **قبل از** جابه‌جایی پوشه‌ها انجام شود.
5. وب‌روت را عوض کنید: روش A یا دستور روش B یا روش C.
   - وردپرس فقط تغییر نام می‌دهد به `wordpress-old` و حذف نمی‌شود.
6. در پنل: تنظیمات › **ایندکس موتورهای جست‌وجو را روشن کنید.**
7. تست بخش ۱۰ را با `https://sajadmasoumi.com` اجرا کنید و گزینهٔ **expect_indexing** را روشن کنید. همهٔ موارد باید OK باشند.
8. Cron دائمی (بخش ۸) را با مسیر `site` بسازید.
9. **دامنهٔ `.ir`:** اگر روی همین حساب است، در وب‌روت آن فقط این `.htaccess` را بگذارید:

   ```apache
   RewriteEngine On
   RewriteRule ^(.*)$ https://sajadmasoumi.com/$1 [R=301,L]
   ```

   مسیرها حفظ می‌شوند. نشانی‌های قدیمی `.ir` به همان مسیر در `.com` می‌روند و آنجا قوانین انتقال اعمال می‌شود.
10. چند روز بعد: اگر مشکلی نبود، می‌توانید `wordpress-old` و دیتابیس وردپرس را بایگانی کنید. **فقط بعد از دانلود پشتیبان** این کار را بکنید.

## ۱۵. بازگشت (Rollback)

| روش | برگرداندن وردپرس |
|---|---|
| A | Document Root را به `public_html` برگردانید. |
| B | `rm ~/domains/sajadmasoumi.com/public_html && mv ~/domains/sajadmasoumi.com/wordpress-old ~/domains/sajadmasoumi.com/public_html` (با Cron یک‌باره یا SSH) |
| C | فایل‌های سایت جدید را از وب‌روت بیرون ببرید و فایل‌های وردپرس را برگردانید. |

دیتابیس وردپرس در هیچ مرحله‌ای تغییر نکرده است.

## ۱۶. به‌روزرسانی‌های بعدی

1. پیش از به‌روزرسانی: `app:backup`، یا مطمئن شوید پشتیبان امروز وجود دارد.
2. بستهٔ جدید را دانلود کنید و SHA-256 را بررسی کنید.
3. آن را روی پوشهٔ پروژه استخراج کنید و فایل‌های موجود را جایگزین کنید. این پوشه‌ها و فایل‌ها **دست نمی‌خورند:**
   - `.env`
   - `storage/`
   - `public/media/`
   - `public/wp-content/uploads/`
   - `public-path.php` و `app-path.php`
4. `app:deploy` را با Cron یک‌باره اجرا کنید. اجرای دوباره همان نسخه هیچ کاری نمی‌کند.
5. تست بخش ۱۰ را اجرا کنید.
